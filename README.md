# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут создавать новые датчики для мониторинга и управления отоплением через API (POST /api/v1/sensors)
- Пользователи могут обновлять параметры датчиков (название, тип, местоположение, единицы измерения) через API (PUT /api/v1/sensors/:id)
- Пользователи могут управлять состоянием отопления, изменяя статус датчиков (active/inactive) и их значения через API (PATCH /api/v1/sensors/:id/value)
- Пользователи могут удалять датчики из системы через API (DELETE /api/v1/sensors/:id)
- Система поддерживает хранение информации о датчиках в базе данных PostgreSQL (таблица sensors)
- Система поддерживает синхронное взаимодействие с датчиками - сервер запрашивает данные у датчиков по требованию
- Система поддерживает управление статусом датчиков (active/inactive), что позволяет включать и выключать отопление
- Система поддерживает отслеживание времени последнего обновления данных для каждого датчика

**Мониторинг температуры:**

- Пользователи могут получать список всех датчиков температуры с актуальными данными через API (GET /api/v1/sensors)
- Пользователи могут получать информацию о конкретном датчике по его идентификатору через API (GET /api/v1/sensors/:id)
- Пользователи могут получать данные о температуре по местоположению (комната, зона) через API (GET /api/v1/sensors/temperature/:location)
- Система поддерживает получение данных о температуре в реальном времени через внешний API (TemperatureService), который обращается к temperature-api на порту 8081
- Система поддерживает автоматическое обновление данных о температуре при каждом запросе информации о датчике - данные запрашиваются у внешнего API и обновляются в ответе
- Система поддерживает хранение метаданных о датчиках: идентификатор, название, тип, местоположение, единицы измерения (°C), статус, время последнего обновления, время создания
- Система поддерживает индексацию датчиков по типу, местоположению и статусу для оптимизации запросов

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

  - поддомен регулирования отпирания/запирания ворот
  - поддомен мониторинга текущего состояния ворот
- домен: наблюдение за домом
  - поддомен регулирования видеокамер 
  - поддомен мониторинга дома

  - поддомен установка устройств в доме
    - контекст регистрация устройства
    - контекст настройка устройства
    - контекст удаление устройства


### **4. Проблемы монолитного решения**

- Высокий риск ошибок
  - Изменение в сервисе по работе со светом могут внезапно сломать отопление (как пример)
- Длительные циклы разработки и развёртывания
  - Каждая новая фича будет затрагивать общий релиз монолита. Значит, каждый раз придётся гонять регрессию по всем сервисам, даже если мы меняли только одну 
- Трудно управлять командой
  - Команда отвечающая за камеры (условно) не сможет выпускать изменения независимо от команды отвечающей за отопление, потому что общий деплой и общий цикл тестирования
- Трудно масштабировать отдельные компоненты системы
  - При высокой нагрузке только на 1 сервис, придется масштабировать все приложение целиком

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры

Ревьюер будет проверять точно так же.
